## 一分钟项目介绍

EchoMind 不是单纯聊天页面，而是一套面向客服的 Agent 编排系统。请求进入 FastAPI 后先读取 Redis/Chroma 的会话与画像，通过 LLM、Embedding 和规则三路融合识别意图，再路由到 General、Technical、Billing 或 Escalation Agent；Agent 可以调用 RAG、本地业务工具和白名单 MCP 工具，最后把回复、状态和工具轨迹原子提交。Vue 前端支持聊天、知识库、评测和请求追踪。现有系统已经有幂等、会话并发控制、缓存/single-flight、熔断、评测与 Prometheus；我规划的下一步重点是流式事件链路、版本化质量门禁和安全语义缓存，让项目从“功能丰富”变成“质量、性能和成本可证明”。

## 高频追问与回答要点

### 1. 和普通 RAG 聊天机器人有什么区别？

普通 RAG 多是“检索后生成”。EchoMind 先做多源意图识别和 Agent 路由，再由 Agent 自主调用受限工具；还处理会话状态、幂等、副作用安全、主辅 Agent、评测和在线降权。RAG 是工具之一，不是整条链路。

### 2. 为什么意图要 LLM + Embedding + Pattern 三路？

LLM 语义强但慢且有波动；Embedding 对稳定相似表达成本低；Pattern 对 401、退款、转人工等高精度词可快速细化。融合能在准确性、延迟与可解释性之间取平衡，但权重不是拍脑袋，应由标注集验证。

### 3. 为什么不直接让前端 POST 一个流式 `/chat`？

浏览器原生 EventSource 不能 POST 请求体。创建 Run 再 GET SSE 能支持认证、断线恢复、查询/取消和任务生命周期；代价是多一个 API 和状态存储，适合当前需要轨迹与可靠性的场景。

### 4. `client_request_id`、`run_id`、`request_id` 为什么要三个？

`client_request_id` 是业务幂等键；`run_id` 是一次异步/流式任务的生命周期；`request_id` 贯穿日志和 Trace。混用会导致重连时重复执行或无法关联排障。

### 5. 断线重连会不会重复调用模型或工具？

不会因为 SSE 重连重新启动 Run。事件先存 Redis Stream，客户端携带 Last-Event-ID 只重放缺失事件；业务执行由 Run 状态机和现有幂等回执保护。

### 6. 取消请求时，工具已经修改了数据怎么办？

不能承诺回滚。副作用工具执行前先持久化 marker；取消后返回 `outcome_unknown` 或工具最终状态，要求核验后再重试。只读工具和模型流可以安全取消。

### 7. 为什么现有缓存还要做语义缓存？

现有缓存解决完全相同查询，价值已经被历史数据证明。语义缓存探索同义改写复用，但风险更高，所以必须限定只读 FAQ、版本化 key、关键实体/否定一致性和对抗集 0 高风险误命中。

### 8. 为什么不直接缓存最终答案？

最终答案可能依赖用户画像、会话、时间和业务状态。首选缓存检索候选；只有完全无个性化、只读、同版本政策问答才考虑最终回答缓存。

### 9. LLM-as-a-Judge 可靠吗？

不把它当唯一真相。先做路由、工具、实体、安全等确定性断言；Judge 只评语义质量，并版本化模型/Prompt/Few-shot、重复运行、报告错误和区间。Judge 失败绝不默认通过。

### 10. 8/8 通过、90.9% 准确率是否说明效果很好？

只能说明现有小样本基线可用。意图仅 11 条，8/8 也可能掩盖覆盖不足；面试中应主动讲样本量、分层困难集、混淆矩阵和置信区间，而不是夸大泛化能力。

### 11. 如何控制在线评测费用？

PR 跑 mock 和确定性小套件；真实模型评测放在手动/夜间 Workflow，设置最大 case、Token 和并发预算。报告用 provider usage，未上报重试不伪造费用。

### 12. OpenTelemetry 会不会泄漏用户数据？

默认不记录 Prompt/回答正文；用户 ID 做 HMAC，订单等实体只记录类型或脱敏摘要。模型、Agent、Tool、状态、Token、耗时是低风险结构化属性，高基数内容不进 metric label。

### 13. 如果高并发 SSE 连接很多怎么办？

API 层需要连接上限、心跳、背压和慢消费者处理；事件存 Redis Stream 后实例可水平扩展。先用 1/10/30 并发压测，不在没有数据时声称支持万级连接。

### 14. 为什么不用 Kafka？

当前是单机面试项目，Redis 已经承担状态与协调，Redis Stream 足以支撑可恢复事件流。Kafka 会增加运维和一致性复杂度；只有跨服务高吞吐、长保留和独立消费组需求出现时再考虑。

### 15. 最大技术债是什么？

当前最大问题不是功能少，而是环境和证据不可一键复现、评测版本信息不足、前端 `App.vue` 过重、在线 Job/指标偏进程内。优先补基线和质量门禁，再做架构扩张。
